# CTGoodJobs Per-Request Proxy Rotation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task.

**Goal:** Implement request-level proxy rotation for CTGoodJobs so every registry, listing-page, and detail-page fetch uses a freshly allocated proxy lease.

**Architecture:** Add a provider-agnostic proxy orchestration layer in the backend scraper stack, then route all CTGoodJobs headless fetches through it. Keep parser and storage contracts stable, demote headed/manual verification to fallback, and add health scoring plus quarantine so request-level rotation remains tunable.

**Tech Stack:** Python, `httpx`, existing crawler workers/spiders, existing runtime capability reporting, optional `jhao104/proxy_pool`-style HTTP API provider.

---

## Summary

- CTGoodJobs will use `rotate_every_request` for registry, listing, and detail fetches.
- Main execution path shifts to headless/request-based fetching; headed mode remains available only for debug or fallback.
- Proxy sourcing stays provider-agnostic, but health scoring, quarantine, and source-specific policy live inside this repo.

## Key Changes

### 1. Proxy orchestration layer

- Add a focused proxy module under `backend/app/scraper/` with:
  - `ProxyProvider`
  - `ProxyLease`
  - `ProxySelectionPolicy`
- Support at least these provider shapes:
  - static/commercial residential proxy endpoint
  - local pool API compatible with `proxy_pool`-style `/get` and optional `/delete`
- Treat every CTGoodJobs request as independent. No lease reuse across registry, listing pages, detail pages, or retries.

### 2. Health scoring and quarantine

- Add a lightweight health service, initially worker-local and memory-backed.
- Track per proxy identity where available:
  - success count
  - challenge/interstitial count
  - connect/timeout count
  - HTTP `403/429` count
  - HTTP `5xx` count
  - last used timestamp
  - quarantine-until timestamp
- Initial scoring:
  - success without challenge: `+1`
  - challenge/interstitial: `-3`
  - connect/read timeout or protocol error: `-2`
  - HTTP `403/429`: `-3`
  - HTTP `5xx`: `-1`
- Initial quarantine:
  - 2 consecutive challenge outcomes: quarantine 15 minutes
  - 2 consecutive network failures: quarantine 10 minutes
  - poor recent success rate: deprioritize before hard-delete

### 3. CTGoodJobs fetch path refactor

- Refactor `backend/app/scraper/ctgoodjobs/html_fetcher.py` so each call:
  - acquires a fresh proxy lease
  - uses that lease to build request transport/client config
  - reports success, failure, or challenge outcome back to health scoring
- Route these CTGoodJobs fetches through the same proxy-aware path:
  - registry page
  - each listing page
  - each detail page
- Keep existing interstitial detection logic, but classify it as a proxy health signal in addition to retry/failure behavior.
- Keep parser outputs unchanged in:
  - `backend/app/sources/ctgoodjobs/parsers.py`
  - downstream canonicalization / persistence contracts

### 4. Spider and worker routing

- Change `backend/app/crawl_modes.py` so CTGoodJobs defaults to `headless`, not `headed`.
- Update `backend/app/services/runtime_capabilities_service.py` so:
  - `ctgoodjobs.default_crawl_mode = headless`
  - `headed_supported = true` remains only as fallback capability
- Keep `backend/crawler/job_crawler/spiders/ctgoodjobs_spider.py` as the primary CTGoodJobs path.
- Keep `backend/crawler/job_crawler/spiders/ctgoodjobs_headed_spider.py`, but narrow its role to:
  - parser/debug research
  - emergency verification experiments
  - manual anti-bot diagnosis

### 5. Configuration surface

- Add explicit CTGoodJobs proxy config in `backend/app/config.py` and `.env.example`:
  - `ctgoodjobs_proxy_enabled`
  - `ctgoodjobs_proxy_provider`
  - `ctgoodjobs_proxy_static_url`
  - `ctgoodjobs_proxy_pool_api_base_url`
  - `ctgoodjobs_proxy_pool_get_path`
  - `ctgoodjobs_proxy_pool_delete_path`
  - `ctgoodjobs_proxy_request_timeout_s`
  - `ctgoodjobs_proxy_quarantine_minutes_challenge`
  - `ctgoodjobs_proxy_quarantine_minutes_network`
- Optional but useful:
  - `ctgoodjobs_proxy_min_seconds_between_reuse`
  - `ctgoodjobs_proxy_require_https_capable`
  - `ctgoodjobs_proxy_provider_auth_header`
- Do not rely on global `HTTP_PROXY` / `HTTPS_PROXY` env vars for this feature.

### 6. Observability and metrics

- Add crawl/runtime metrics for CTGoodJobs proxy behavior:
  - `proxy_requests_total`
  - `proxy_requests_success`
  - `proxy_requests_challenge`
  - `proxy_requests_network_fail`
  - `proxy_requests_http_fail`
  - `proxy_quarantined_total`
- Record metrics by stage:
  - `registry`
  - `category_page`
  - `detail_page`
- Include proxy-enabled/provider metadata in `crawl.started` payloads for CTGoodJobs runs.

### 7. Manual action and fallback behavior

- Do not treat manual verification as durable state for future rotated requests.
- Keep existing `ManualActionRequiredError` plumbing intact for headed/debug paths.
- For normal headless CTGoodJobs runs:
  - challenge hit => classify as proxy outcome
  - retry using a new lease
  - only escalate to manual action from explicit fallback/debug flows

## Test Plan

### Unit tests

- Provider selection and lease creation
- pool API provider parsing of `/get` responses and optional `/delete`
- health scoring transitions for:
  - success
  - timeout/network error
  - HTTP `403/429`
  - challenge/interstitial
- quarantine behavior and expiry
- no lease reuse across consecutive CTGoodJobs requests

### Fetcher tests

- `html_fetcher` acquires a fresh lease for each call
- retries after challenge/network failure use a new lease
- success reports health outcome once
- challenge HTML reports `challenge_detected=True`
- HTTP status failures and network exceptions produce expected health events

### Spider and worker tests

- CTGoodJobs headless spider fetches registry, listing pages, and detail pages with independent lease acquisition
- progress and metrics continue to update correctly
- default crawl mode resolution now returns `headless` for CTGoodJobs
- runtime capabilities advertise the new default mode

### Integration / PoC scenarios

- Run the same CTGoodJobs categories/pages through:
  1. current baseline without proxy rotation
  2. full per-request rotation without quarantine
  3. full per-request rotation with quarantine enabled
- Measure:
  - registry success rate
  - listing page success rate
  - detail page success rate
  - interstitial/challenge hit rate
  - average attempts per successful page
  - usable-proxy ratio over time

## Assumptions and Defaults

- Scope is CTGoodJobs only for now, though abstractions should be reusable.
- Every CTGoodJobs request rotates, including registry, listing, detail, and retries.
- Headed/manual verification remains supported but is no longer the primary CTGoodJobs path.
- `jhao104/proxy_pool` is treated as a provider/backend option, not as the top-level source-specific policy engine.
- Initial proxy health state can be worker-local and in-memory unless testing proves shared durable state is needed.
