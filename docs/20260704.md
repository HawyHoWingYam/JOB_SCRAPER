# OfferToday 修改計劃 — 2026-07-04

## 背景

max_pages=50 的 crawl 成功抓到 **3001 個獨立 IT job ID**（1676 頁），確認 3000 目標完全可達。
同時確認 OfferToday 底層是 BOSS 直聘，所有請求先過阿里雲 WAF（`/web/passport/cm/verify.html`）。
**全力方向：headed Windows 本機**，Docker headless 在 TLS 層直接被攔，不可行。

## 問題一：Crawl 達到 3001 IDs 但狀態顯示 `failed`

### 現象

Crawl job `9b50d653` 完成 1676 頁、收集 3001 個 unique IDs，但最終狀態為 `failed`，
錯誤訊息：`"Service restarted before crawl job could finish."`

### 根因

Listing phase（收集 job IDs）已完整完成，但 service 在 detail phase 期間重啟，
導致 job 整體被標為 failed。Listing 成果無法存活過重啟。

### 修改計劃

| 步驟 | 做什麼 | 檔案 |
|------|--------|------|
| 1 | 在 listing phase 完成時，立即 commit 一個 `listing_completed` checkpoint event | `offertoday_standalone_crawl.py` |
| 2 | 若重啟後 job 已有 `listing_completed` event，前端顯示為「部分完成」而非 `failed` | `backend/app/api/crawl_jobs.py` |
| 3 | 或者：把 listing 和 detail 分成兩個獨立 job（like 現在 JobsDB 做法），讓 listing job 單獨顯示為 `completed` | 架構層改動 |

**建議：** 先做步驟 1+2（快），再評估步驟 3（穩）。

## 問題二：前端 Target Sectors 顯示 ERP

### 現象

Direct Override 面板的 Target Sectors 只顯示一個 "ERP" 核取方塊，而非預期的 31 個分類。

### 根因（已確認）

**測試 mock 產生的視覺假象，不影響生產環境。**
`ScheduleManager.test.jsx:129` 有：

```javascript
const OFFERTODAY_CATEGORIES = [{ id: 101000, name: 'ERP' }];
```

這個 mock 只在執行 Vitest 測試時出現，生產 API 正確返回 31 個分類（含 Information Technology = 118000）。

### 真正的 UX 問題（需修復）

前端 `buildImmediateScrapePayload` 在 `crawl_phase=listing` 時強制要求選至少一個 sector，
但 OfferToday 最優的全覆蓋爬蟲是用**空 `category_ids`** 傳給後端，
由後端自動展開全 IT family（23 個 category + 18 個 keyword + 6 個 hybrid）。

### 修改計劃

| 步驟 | 做什麼 | 檔案 |
|------|--------|------|
| 1 | 為 OfferToday 加入「全 IT 分類（預設）」選項，值為空陣列，前端顯示為已選 | `ScheduleManager.jsx` |
| 2 | 當 source=offertoday 且 crawl_phase=listing 且 category_ids=[] 時，跳過「必須選 sector」驗証 | `ScheduleManager.jsx:144` |
| 3 | 更新測試 mock 名稱為更真實的值（如 `Information Technology`）避免未來混淆 | `ScheduleManager.test.jsx:129` |

## 問題四：IP 封鎖讓 detail phase 靜默失敗（2026-07-04 新增）

### 現象

Crawl job `5f0af877` 的 listing phase 正常，收集到約 2000 個 unique IDs。
Detail phase 開始後，`detail_completed` 停在 **1052**，`detail_failed` 累計 **188**，
`detail_pending` 還有 **763** 筆仍在跑（到 08:02 最後更新時）。
直接打 OfferToday detail API 測試，成功和失敗各一筆都回：

```
code = -1000035，訊息：IP 行為異常
```

### 根因

站方從 API 層封鎖了 IP。這與 WAF 的 browser redirect challenge 不同：
- WAF 封鎖：瀏覽器被導向 `/web/passport/cm/verify`，現有的 `_check_and_handle_waf_challenge` 偵測得到
- IP 封鎖：detail JSON API 直接回 `{"code": -1000035}`，**現有 WAF 偵測完全看不到這個路徑**

目前 standalone script 的 detail loop（`offertoday_standalone_crawl.py:587`）只判斷 `code == 0` 算成功，
任何非 0 都標 `failed`，但不區分錯誤原因，也不提前中止。
結果：IP 被封後仍繼續打了 763 個無效請求，每筆都在等 3 次 retry + exponential backoff，
浪費大量時間，且 UI 只看得到 `detail_failed` 數字在增加，看不出是 IP 封鎖。

### 診斷補充：Job Browser 看不到資料

另一個症狀：Job Browser 第一頁看不到剛爬的 OfferToday 資料。

**根因（已修復 ✅）**：OfferToday 的 `posted_date` 全為 NULL，
後端原本用 `posted_date DESC NULLS LAST` 排序，把這批資料全推到最後一頁。
已改為 `COALESCE(posted_date, created_at) DESC`（`backend/app/api/jobs.py:554`），
令 `posted_date` 空白的資料改用 `created_at` 作後備排序鍵。

**注意**：Job Browser 目前只在 mount 時抓一次資料，不會自動 live refresh。
如需看最新資料，需手動重新整理頁面或提交搜尋。

### 修改計劃

| 步驟 | 做什麼 | 文件 |
|------|--------|------|
| IP-1 | detail loop 偵測 `code == -1000035`，連續 2 次後視為環境性封鎖 | `offertoday_standalone_crawl.py:587` |
| IP-2 | 確認是 IP 封鎖後：寫 `crawl.ip_blocked` 事件到 DB（含 error code、已處理 index） | `offertoday_standalone_crawl.py` |
| IP-3 | bulk update 剩餘 `pending` listings 為 `failed`（一條 SQL，非逐筆迴圈） | `offertoday_standalone_crawl.py` |
| IP-4 | Break 出 detail loop，在最終 `crawl.completed` event 帶上 `ip_blocked: true` | `offertoday_standalone_crawl.py` |
| IP-5 | `progress.py` 加入 `crawl.ip_blocked` 到 context event types，新增 `ip_blocked` 欄位到 snapshot | `backend/app/api/progress.py` |
| IP-6 | 前端在 detail phase 顯示 IP block banner（類似現有 WAF banner） | `ScrapeProgressPanel.jsx` |

### 附：pageSize 分叉 bug

同次排查發現：standalone script 有自己的 private `_build_listing_payload`，`pageSize` 寫死為 **10**，
而最近 commit 把 `constants.py`（Scrapy spider 用）改為 `pageSize: 50`。
兩者分叉後 standalone 每頁只拿 10 筆，需要 5× 請求量才能覆蓋同樣資料，WAF 風險大增。

修法：刪除 standalone 的 private payload builder，改 import `constants.build_offertoday_listing_payload`。
