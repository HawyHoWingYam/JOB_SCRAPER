# OfferToday Search Coverage Expansion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the OfferToday backend crawl enumerate the full IT search surface, not just ERP. Preserve the observed ERP keyword-only coverage at 598 job IDs and push the default IT crawl without user-supplied keywords toward 3000 unique job IDs when the source has that much reachable inventory.

**Architecture:** Treat OfferToday as three overlapping search families instead of one flat crawl: an IT category sweep, an IT keyword sweep, and a small set of high-signal hybrid probes. The planner must return labeled query records so crawler metrics and live audits can separate family contributions. Keep `max_pages` as a per-search-condition limit, dedupe by `source_job_id` across every family before persistence, and stop by unique-job threshold rather than by a single global page budget. Keep Scrapling only as a listing/detail fallback when the primary fetch path is blocked.

**Tech Stack:** Python 3.11, FastAPI, SQLAlchemy 2.0, Scrapy, Playwright, Scrapling, pytest, httpx.

---

## Purpose And Scope

### Overall Purpose

Close the gap between what OfferToday exposes on the live site and what the backend crawler currently collects. The user has two concrete expectations:

- ERP keyword-only searches should yield at least 598 job IDs in the backend.
- Default IT crawls, without a manually supplied keyword, should collect far more than the current category-only crawl and should be able to reach 3000 unique job IDs if the live source still has that much inventory.

### This Iteration's Purpose

This branch is not a full crawler rewrite. Its purpose is to make OfferToday coverage measurable and complete enough to trust:

- Keep the current Playwright + Scrapling transport path alive.
- Expand the search space so we stop undercounting IT jobs.
- Keep explicit keyword probes pure when the caller asks for a single term such as `ERP`.
- Add enough audit data to explain why a crawl got a specific count.

### Non-Goals

- Do not migrate other sources in this branch.
- Do not replace the crawl control plane.
- Do not remove Playwright unless the measurement work proves a safer fallback.
- Do not change JobsDB or CTGoodJobs semantics unless a shared request schema field must remain source-aware.

### Success Definitions

- `ERP` keyword-only search: backend crawl reaches at least 598 unique job IDs.
- Default IT crawl: backend crawl reaches 3000 unique job IDs if the live source still exposes that inventory.
- Search planner: emits labeled search families and dedupes across families before persistence.
- Verification: every change has a unit test and the live audit script proves the coverage count.

## 1. Current Evidence

Live checks taken on 2026-07-02 show:

- `keyword="ERP"` with no `jobFunctionCodes` returns `total=598` on OfferToday.
- `keyword="IT"` with no `jobFunctionCodes` returns `total=606` on OfferToday.
- Several other broad IT probes also return hundreds of results on page 1, including `software`, `data`, `support`, `network`, `security`, `project`, `web`, and `testing`.
- `jobFunctionCodes=[118000]` with blank keyword returns `total=606` on the first page for the IT root.
- The static OfferToday IT registry has 23 codes total: one root (`118000`) plus 22 leaf categories.
- `jobFunctionCodes` can be omitted entirely and OfferToday still returns results, so keyword-only crawling is a real mode, not a hack.
- A blank-keyword IT-family sweep by category alone is not enough to reach the user's desired 3000-job target. In one live sample, the first-page `total` values across the IT family summed to 2066 before deduplication, which is still below the target and still not unique.
- A broad IT keyword sample across the first three pages of each keyword produced a much larger unique pool than the IT category tree alone, which is why keyword-only discovery is required.

Conclusion: the current code already proves that category-only crawling is incomplete. The next step is not "more pages everywhere"; it is a broader search plan that combines category coverage with keyword-only discovery.

## 2. Design Choice

Recommended approach:

1. Run the IT category tree first.
2. Run an internal IT keyword pack when no explicit keywords are supplied.
3. Keep explicit keyword probes untouched when the caller asks for a specific term such as ERP.
4. Deduplicate globally before staging listings or saving jobs.

Search families:

| Family | Input shape | Why it exists | Expected output |
|---|---|---|---|
| `it_category` | `category_id` expanded from `118000`, blank keyword | Captures structured IT inventory inside the official category tree | Broad IT job IDs with stable classification |
| `it_keyword` | `category_id=None`, default IT keyword pack, blank or omitted explicit keyword input | Captures IT jobs that are not indexed cleanly under IT categories | Additional job IDs that category-only crawling misses |
| `explicit_keyword` | caller-supplied term such as `ERP` | Preserves exact user intent for narrow searches | Pure keyword-only coverage for the requested term |
| `it_hybrid` | small targeted category + keyword intersections, only if needed | Optional top-off when category + keyword are still short of target | High-signal overlap between category and keyword views |

Trade-off:

- Pure category expansion is simple, but it leaves a lot of IT jobs outside the tree.
- Pure keyword expansion finds more jobs, but it can miss structured category-only inventory.
- The hybrid plan costs more requests, but it is the only approach that can plausibly satisfy both requirements: 598 for ERP and much broader default IT coverage.

## 3. Success Criteria

- ERP keyword-only runs keep returning at least 598 unique OfferToday job IDs.
- Default OfferToday IT crawls without user-supplied keywords collect at least 3000 unique job IDs if the live source still exposes that much inventory.
- Duplicate `source_job_id` values are suppressed across all search families in one crawl run.
- `max_pages` remains a per-search-condition limit, not a global crawl budget.
- The crawler records enough metrics to explain which family contributed which IDs.
- All new behavior is covered by tests plus one live coverage audit script.

## 7. Risks And Fallbacks

| Risk | Impact | Fallback |
|---|---:|---|
| The default IT keyword pack returns too many duplicate IDs | Medium | Reorder the pack by yield and stop earlier once the unique-ID curve flattens. |
| The IT category tree plus keyword pack still does not reach 3000 | High | Expand the keyword pack in measured rounds with broader IT synonyms before touching unrelated sources. |
| The ERP probe drops below 598 after the planner change | High | Treat that as a regression and fix the planner ordering before shipping. |
| API threading accidentally changes JobsDB or CTGoodJobs behavior | Medium | Keep the new keyword field OfferToday-only and add a regression test for the other sources. |

## 8. Scope Boundaries

This plan only changes OfferToday search coverage. It does not attempt to refactor the rest of the crawl modernization work, and it does not change the existing JobsDB or CTGoodJobs crawling strategies unless they share a request-schema field that must remain source-aware.
