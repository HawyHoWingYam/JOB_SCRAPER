### 推进纪律：以关闭交付为主

已经识别的执行问题是：重复审查、上下文重载和重复验证消耗了过多时间，形成“持续打磨当前 checkpoint，但没有足够快地关闭并进入下一交付”的停滞。后续必须按以下规则推进：

1. **进度只按可验收交付计算。** 主要指标是 checkpoint/task 是否实现、通过必要门并提交，不把阅读轮次、审查次数、测试运行次数或代码行数当作进度。
2. **一个 checkpoint 只走一条主闭环。** 实现 → focused gate → 修复具体失败 → 一次最终 full gate → 更新任务记录 → commit。没有新的失败证据时，不重复启动同质审查或重新跑同一组广泛检查。
3. **审查必须产生可执行 finding。** 只处理有 `file:line`、可复现路径和真实 contract 影响的问题；泛化建议、假设性边缘风险和不影响当前验收的重构不阻止 checkpoint 提交，必要时记录为后续项。
4. **上下文只在边界变化时重载。** 仅在切换 package/task、发现契约矛盾或现有证据失效时重新读取 foundational docs；不得在同一 checkpoint 内反复重读已经确认的任务与规范。
5. **验证按风险分层。** 开发中运行直接相关测试；checkpoint 收尾运行 touched Ruff/mypy/compileall、focused regressions 和一次 full suite；PostgreSQL、migration、live smoke 与 destructive rehearsal 只在相应 checkpoint 的验收门执行。
6. **已完成 checkpoint 默认不重新打开。** 只有当前实现提供了明确 regression 证据时才回退；否则继续下一 checkpoint，避免在已通过范围内无限追求额外完善。
7. **优先消灭关键路径上的未完成项。** Checkpoint 7–9 已按顺序关闭；当前关键边界是需要单独批准的 rollout/cutover，不重新打开已通过的后端 checkpoint。
8. **每次进度更新必须回答三个问题。** 刚关闭了什么、现在唯一的主交付是什么、关闭它还缺哪些具体证据。若连续更新没有 checkpoint/task 状态变化，必须立即检查是否陷入重复审查或过度验证。

这些纪律的目标不是降低质量门，而是让验证集中在真正决定验收的证据上，并持续把在制工作转化为已提交、可继续依赖的交付。

### 2. Source-native 分类模型

- JobsDB、CTgoodjobs、OfferToday 各自保留独立的原生分类树，不因为名字相似就强行合并。
- 每个可选择节点都有 source-qualified identity，例如：
  - `jobsdb:6281`；
  - `ctgoodjobs:021`；
  - `offertoday:118000`。
- 节点保存 native ID、label、path、parent、depth、exact/subtree/query capability、alias 与 query-semantics fingerprint。
- 支持 `all`、`exact` 和 `subtree` 三种 scope expansion，并保证每个 queryable classification 只执行一次。
- OfferToday 的 same-code child 会保留供审计，但作为 non-selectable alias，不会产生重复 Query Target。
- OfferToday UI 推荐范围仍是 `offertoday:118000` 的 IT subtree；推荐值不是隐藏默认值，也不是运行时权威。

### 3. 三个生产 Source Catalog Adapter

- JobsDB Adapter：发现原生分类，并编译成带 `classification=<native_id>` 的 Query Target。
- CTgoodjobs Adapter：发现分类和真实 URL path；bundled static registry 只允许作为 candidate discovery seed/fallback，并记录 provenance，绝不作为 runtime fallback。
- OfferToday Adapter：保存 root、unique leaves 和 aliases，编译为带 `jobFunctionCodes` 的 bounded category request。
- Runtime 不会调用 `discover()`；只有 governance/operator 流程可以发现 candidate。

### 4. Crawler 运行时对齐

#### JobsDB

- Standalone 和 Scrapy 共用权威 request builder。
- 用户选择不同 classification 时，最终 outbound request 的 `classification` 参数确实不同。
- Source Classification 会随 listing/staging metadata 保存。

#### CTgoodjobs

- 继续保持 headed-only，暂时不改成 headless。
- Standalone 和 Scrapy 只使用 active published revision 中保存的 URL path。
- 未知 ID 会在浏览器请求之前失败，不再把 raw ID 当 slug 猜 URL。
- 需要登录、WAF 或人工操作时仍走 manual-action 流程。

#### OfferToday

- Published classification 会真正进入请求的 `jobFunctionCodes`。
- Classification-only scope 不会偷偷加入 categoryless keyword queries。
- 显式 keyword request 继续保留旧行为，但如果同时提供 classification，必须先通过 active revision 验证。
- Root exact、subtree、all-scope、unique leaf 与 alias dedup 都已有 deterministic tests。

### 5. Durable Validation

- 每个 Candidate 会执行一次 full-catalog offline validation。
- Added 或 query-semantics-changed Query Target 会建立 durable live-smoke validation run。
- Validation 状态支持 `passed`、`failed` 和 `manual_action_required`，失败后可针对同一 target hash 重试。
- Stale worker 不能覆盖已被其他 worker reclaim 的结果。
- Smoke 限制为一个 target/一页；OfferToday 只额外执行必要 warmup，不抓 detail、不写 staging、不发布 catalog。
- Evidence 使用严格 scalar allowlist；body、cookies、auth/session data、browser state、nested payload 和 unbounded ID list 不会持久化或写日志。

### 6. 发布与回滚安全门

- Publish/Rollback 需要短期、single-use、actor-bound review token。
- Review 会绑定 candidate/revision fingerprint、当前 active base revision 与 Automation impact digest。
- 真正修改 pointer 前会再次计算 Automation impact；digest 或 active revision 改变就返回 `CATALOG_IMPACT_STALE`。
- Production 中没有 permissive/no-op impact evaluator。
- 在 Versioned Crawl Scope 提供真实 impact evaluator 之前，首次生产发布会保持 blocked。


### 3. PostgreSQL schema 与不可变历史

- Foundation 新增 Alembic revision：`20260718_210000`。后续 domain children 已继续追加 migration，当前 repository Alembic head 为 `20260719_160000`。
- 新增三张共享表：
  - `governance_revisions`；
  - `governance_audit_events`；
  - `governance_idempotency_records`。
- Revision 对 `(domain, release_key)` 与 `(domain, content_hash)` 分别唯一；exact publication replay 返回原 `RevisionRef`，不能把 release key 或 content hash 重新绑定到另一份内容。
- Revision、audit 与 idempotency rows 同时受 ORM guard 和 PostgreSQL trigger 保护，不能 update/delete。
- Audit 不使用会随 subject 删除而 cascade 的 FK；即使 domain subject 退休，actor、before/after、evidence、command hash、correlation/idempotency 与时间仍保留。
- 没有创建 generic evidence table 或 generic taxonomy-node table；domain evidence 仍由各 child 自己拥有。

### 4. Human decision transaction

`GovernanceUnitOfWork.execute` 的事务顺序已经固定并测试：

1. 要求 `confirmed=true`；
2. 要求 `actor=local-operator`；
3. 对 `(domain, idempotency_key)` 序列化并检查 exact replay/conflict；
4. 由 domain adapter `load_for_update`，检查 `expected_version`；
5. domain adapter 执行自己的 transition，但不能独立 commit；
6. 校验返回的 subject/version 与持久化状态一致，并要求至少一个 outbox event；
7. 同一 transaction 写入 domain effect、append-only audit、现有 `event_outbox` 和 serialized idempotency result；
8. 只 commit 一次；任一步失败全部 rollback。

已覆盖 exact replay、conflicting replay、stale version、missing confirmation、非法 actor、两个 session 并发、audit 已 flush 后 outbox serialization 失败等场景。失败后不会留下半个 domain effect、audit、outbox 或 idempotency record。
